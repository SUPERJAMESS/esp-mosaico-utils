## 复现范围与故障定义

“多应用分区”分三类记录，避免把不支持的布局当作稳定性故障：

1. 多个独立应用使用相同分区表，来回更新应用代码。
2. 不同应用使用不同 `main_app` 大小或资源分区数量、偏移、内容，通过 System Update 来回切换布局。
3. 同一 NOR 上存在多个普通可启动 app 槽位。当前产品是保留 `vibe_mode` 的单运行槽维护模型，不承诺 A/B 回滚。客户若属于此类，先取得真实分区表并核对产品支持范围；超出契约的包应在写入前明确拒绝，另行记录兼容性问题。

以下任一情况都记录为一次异常，不以重试成功抹掉：

- 命令超过原始期限、无进度、设备长期停在 Vibe Mode，或写入成功后无法验证目标应用。
- 目标 Device ID、镜像 ELF SHA、分区表摘要或资源摘要不符；写到了非目标设备。
- 非目标设备 Boot ID 改变、断连或不可用，或者一台失败阻塞其他设备。
- 需要拔插、按键复位、重启 CLI/Gateway、接管/清理所有权、ROM 恢复或重新烧录才能继续。
- 出现崩溃、不断重启、健康确认失败、保留数据意外改变。

预期的布局不匹配、无目标多设备选择错误、同设备写入冲突应单独计为“正确拒绝”。若拒绝前发生写入、错误绑定目标或留下不可恢复的占用，则计为异常。

## 执行前准备

1. 取得消费工作区根目录及其 `mosaico.py`。所有设备动作均经该 launcher；不直接运行 IDF、esptool 或 Iris 设备写入命令。应用工程、`.mosaico.json`、固件与本机运行记录保留在消费工作区，不加入本 utils 仓库。
2. 在改变现有会话前保存 `iris status --all --json`、USB 树和当前应用信息。记录每台设备的 Device ID、Boot ID 原始文本、Base MAC、当前所有者、Vibe Mode 版本、布局摘要、应用 ELF SHA、可用数据链路与崩溃基线。
3. 记录客户实际操作：串行还是同时烧录、使用 CLI 还是 Workbench、完整命令、固件大小、分区表，以及曾经如何人工救回。若尚无客户包，使用下面的可控样本，并将结果标为合成负载。
4. 为每个测试设备建立身份映射。先保留现场拓扑；未确认身份、旧版契约、无有效数据链路或包校验失败的设备不进入写入阶段。迁移或恢复作为独立前置工作记录。
5. 预构建并冻结全部测试包。记录 `.bin` 和 `.irisfw` 实际字节数、ELF SHA、文件 SHA-256、每个组件的大小/偏移/类型，以及分区表摘要。禁止九个 worker 同时在同一构建目录构建；执行期使用 `--skip-build` 或冻结的 `--bundle`。
6. 首轮使用单个项目 Gateway 管理九台设备，保留一个 `iris run` 前台客户端。下文 `control_project` 指消费工作区当前的 `default_project`，先确认根目录下省略 `--project` 的命令确实解析到该项目。由不同应用的项目 Gateway 接管设备是后续独立实验，不与基本烧录压力混在一起。

更新前审查写入范围。不得清空凭据、设备身份、Vibe Mode 数据或执行全片擦除。布局样本只调整可用于测试的应用及声明资源区，不移动保留系统区；覆盖已有业务资源前明确测试范围。断电、写入中拔线和 ROM `recover` 会改变设备状态，列入单独的故障注入批次，执行前取得相应授权。

## 固件与分区样本

先执行 Vibe Mode 自更新：从当前 utils 源码构建 V-A、V-B 两个镜像，保持固件版本 `0.2.0`，通过重新编译应用描述的构建时间产生不同 ELF 摘要，不修改固件功能或使用评审预编译固件。自更新样本与下表普通应用 A/B 分别管理。

| 自更新测试组 | 并发 | 次数 | 验证 |
| --- | --- | --- | --- |
| S1 | D01 单台，其他八台保持连接 | V-A/V-B 交替安装 10 次 | 新 Boot ID、目标 ELF SHA、healthy、原布局及 bootloader 摘要 |
| S9 | 九台同时自更新 | 每台交替安装 20 次，共 180 次 | 每台独立操作记录、实际写入重叠、重连及健康验证 |

自更新共计划 190 次，先于下文普通应用测试。源镜像为 1,667,600 字节，固定保留槽为 1,835,008 字节；制包器按产品契约补齐槽位。相同摘要会被设备跳过写入，因此每次必须确认当前 ELF 与目标不同，不能把重复提交统计为实际烧写。

首轮并发已触发主机上传接纳问题，现场和手动介入见[自更新问题记录](multi-device-self-update-issues.zh-CN.md)。按用户后续指令从第 2 轮继续：明确的 HTTP 429 提交前拒绝逐次记录并继续下一轮，真正结果不明的操作仍需冻结核对，原失败记录不覆盖。

现场九台使用相同的带资源分区布局。由消费工作区 `projects/hello_world/partitions.csv` 重新生成分区表，确认其摘要与九台 live inventory 均一致后，使用正式制包器的 `--target-layout` 作为自更新前置条件；包中只有一个 `recovery` 组件。该表仅用于校验，不作为写入组件，也不改变源码项目默认布局或评审包。任一首次异常触发冻结并保存现场，后续批次不自动继续。

| 样本 | 内容与大小目标 | 布局及目的 |
| --- | --- | --- |
| A | 最小可运行应用，启动后报告 healthy，能读取自身构建标识 | L1，建立小固件基线 |
| A2 | 与 A 相同布局、不同 ELF SHA 和构建标识 | 验证代码更新和旧镜像误判 |
| B | 与 A 相同布局，应用镜像占 `main_app` 的 85% 至 95% | L1，隔离应用传输大小影响 |
| C | 应用加至少两个不同内容的声明资源镜像，调整应用/资源边界 | L2，验证多组件和分区表切换 |
| D | 在产品允许范围内增加资源组件数或移动资源偏移，总量接近有效布局容量 | L3，验证组件数量、旧资源和边界处理 |
| R | 客户真实应用及其原始分区表和资源 | 作为现场复现主样本，保留原大小和内容 |

“大”以实际未压缩镜像字节数和分区占用率定义，另记包传输大小。首轮只准备小应用和约 90% 占用的大应用，约 25%、60% 的大小分档留作故障定位；实际合法上限以设备 Flash、清单和包校验为准。基线分区表的 `main_app` 大小为 `0xdf0000` 字节，但资源布局可能缩小该槽，不能套用固定的“大于 8 MiB”作为通用要求。

大应用通过编译进镜像的确定性内容构造，资源使用固定种子生成且每版内容不同；禁止在现成 `.bin` 尾部追加垃圾来模拟有效大镜像。C、D 每个资源分区至少保留版本标记和完整摘要验证；资源校验能力须在样本准备阶段落实。保护区和健康确认要求均沿用产品契约。

额外准备两个预期拒绝样本：分区表不同却走 `app-update`、镜像超过目标分区。只在写入前校验能保证拒绝的路径执行，验证明确报错、未写入且设备身份、应用和布局未改变；若检查前进入 Vibe Mode 导致 Boot ID 改变，单独记录该正常模式切换，不据此判为发生写入。

## 标准循环与九设备调度

先通过 `system-update` 把设备放到 A/L1，建立起点。一个标准循环定义为四次安装：

| 步骤 | 目标变化 | 操作 | 必须验证 |
| --- | --- | --- | --- |
| 1 | A → A2 | `system-update --bundle`，相同分区表 | 同 Device ID、新 Boot ID、A2 ELF SHA、healthy |
| 2 | A2 → B | `system-update --bundle`，相同分区表 | 大镜像确实为 B、布局不变、healthy |
| 3 | B → C | `system-update`，L1 → L2 | C ELF SHA、L2 实时分区表和全部资源摘要、healthy |
| 4 | C → A | `system-update`，L2 → L1 | A ELF SHA、L1 实时分区表、healthy，能开始下一轮 |

首轮由更新命令自动切换 Vibe Mode，不额外增加显式切换的完整批次。若失败发生在模式切换阶段，再用更新前显式 `iris test enter-recovery` 作对照；显式切换须验证同一 Device ID 和新 Boot ID，已在 Vibe Mode 则按幂等返回验证当前模式。记录 normal → Vibe Mode → normal 的每段耗时；设备的可用观测接口未提供中间态时，以操作记录及启动日志补全。

标准循环统一使用冻结的 System Update 包，通过同一控制项目 Gateway 提交，隔离多项目接管的影响；同布局 `app-update` 在定向用例中单独比较。每台设备只允许一个写入任务。跨设备并行；每个任务显式指定 Device ID，禁止按串口排序、设备列表下标或“首个可用设备”选目标。`app-update --project` 属于目标应用项目会话，须先完成明确接管或归还，再开始写入；不得假定不同项目自动共享所有权。保存所有权变化，将其耗时与纯更新耗时分开。

九台初始均从 A 起步。同步启动实验用屏障放行，不要求写入阶段严格重合，记录实际写入重叠区间；异步实验使用固定随机种子，每台循环间等待 0 至 3 秒。首次失败立即保存现场，故障设备不自动重烧；其他设备是否继续按下面的故障隔离规则执行。

## 单台与九台并发测试矩阵

按用户最新要求，普通应用后续测试先执行九台批量。批量失败时先保留原操作并确认写入结果，再对故障设备按相同包和前置状态做单台定位；批量全部通过后，仅由 D01 做一次四步标准循环，其余八台保持连接且不写入，作为隔离对照。不再先跑十轮单台，也不轮流对九台各做串行基线。两组使用相同冻结包、循环顺序、超时和验证规则。以下安装次数不包含初始化到 A、已执行的历史单台更新、按需定位和故障注入。

| 测试组 | 连接与并发 | 标准循环数 | 安装次数 | 观察目的 |
| --- | --- | --- | --- | --- |
| T9 | 九台同时更新 | 每台 20 轮，同步与异步各 10 轮 | 720 | 大固件、布局切换、重启枚举和并发竞争 |
| T1 | T9 全部通过后，九台保持原接线，仅 D01 更新 | D01 仅 1 轮 | 4 | 批量后单设备验证；其余八台无意外复位或断连 |

当前 T9、T1 共计划 724 次安装，不强制 8 小时或每台 100 轮长测，完成轮数即结束。此前按旧顺序已通过一轮四步及第二轮前两步，共 6 次单台更新，另有一次初始化，均单独保留，不覆盖或改记。调整调度时等待正在进行的写入完成。实际耗时以测量为准，不能按次数等比推算。首次批量异常触发冻结后回退到故障设备单台定位，不为凑满轮数继续重烧。

T9 的首轮兼作九台身份与更新验证，不再增加独立冒烟批次。九台并发发生异常时直接用故障设备单台复放，不经过其他并发档位；单台复核先解决原操作是否仍在写入及当前镜像状态，不能盲目重放未知结果。批量通过后的单台验证仅做一次循环。两组均未复现则记录本轮结果，不自动追加长测。

以下定向用例只在对应现象出现时选取，不作为首轮必跑项目。先在故障设备单台重放 1 至 3 次，需要并发条件时直接用九台复放，保留实际命中次数：

| 用例 | 操作与对照 | 重点证据 |
| --- | --- | --- |
| 大小方向 | 小 → 大 → 小、大 → 小 → 大；三档占用率分别运行 | 失败是否跟随大小、方向或累计写入量 |
| 资源与布局 | C/L2 ↔ D/L3，组件数和大小分别变化；单独更改资源、保留应用版本 | 逐分区摘要、旧资源被误用、表提交与启动顺序 |
| 相同产物 | 同一包连续安装，与不同 ELF SHA 的交替安装比较 | 幂等/跳过是否正确，是否误报新版本已启动 |
| 代码更新路径 | 相同布局的 A/A2/B 分别走 `app-update` 与 `system-update`；不同项目间明确接管，同项目重复更新作对照 | 代码更新路径是否单独失败，区分接管与传输阶段 |
| 空闲边界 | 有前台客户端时空闲 5/15/30 秒；另设释放最后客户端后的 15/30 秒对照 | Gateway 10 秒空闲退出、客户端续期、重建会话及重新认领 |
| 多项目交接 | 控制项目与另一应用项目之间明确 takeover，再切回 | takeover ID、所有权、端点锁和设备身份连续性 |
| 同设备争用 | 在九台并发批次中，对其中一台额外提交第二个更新 | 同设备拒绝或安全排队，不并发写；其余八台不被堵住 |
| 默认目标歧义 | 无已连接/已认领目标的独立会话省略 Device ID | 多候选时明确拒绝，不能误写任意设备 |
| 客户路径 | 用 R 重放客户命令及布局序列，先原节奏，再扩大并发 | 原始操作是否单独足以触发问题 |

空闲试验中“设备认领”不等于前台保活；结束 `iris run` 后其他客户端或活动操作仍可能保活。以实际 Gateway 状态确认退出，而非只按等待时间推断。默认目标歧义用例须满足无唯一已有连接/所有者的前提，否则自动选择可能是正确行为。

## 故障注入与接线对照

本节为按需定位，首轮不执行。确需验证中断恢复时，对最多一台设备注入，另外八台作为对照。每个选定注入点最多重复三次；操作与时刻单独标注，不能算作自然发生的故障。

| 场景 | 注入点 | 验证要求 |
| --- | --- | --- |
| CLI 中断 | 提交后退出等待客户端 | Gateway 中原操作仍可查询，不产生第二次写入 |
| 等待超时 | 将某次调用等待期限设短，写入器可能仍运行 | 保存原 operation ID，查询最终状态；禁止立即重烧 |
| USB 中断 | 传输开始、接近完成、重启重新枚举各选一次拔插 | 同一设备重连、操作状态可解释、其他设备不受影响；是否需手动介入单独记录 |
| 供电中断 | 应用写入、资源写入、布局提交附近 | 单运行槽维护行为符合契约；不得要求不存在的 A/B 回滚 |
| Gateway 异常退出 | 提交后及重连验证期间分别终止测试 Gateway | 保留写入器/锁和原记录，恢复查询或验证，不重复提交 |

USB 拔插不一定切断电池供电；断电用例必须记录实际电源路径。未获得保护数据范围和注入授权时，跳过相应批次并记为未覆盖。

若异常与并发相关，保持同一设备、同一包、相同种子及超时，逐项比较：当前九台接线、仅保留一台连接、单层外供电 Hub、跨已确认独立的 USB 控制器分摊、换线/换 Hub 端口。每次改变一项，记录故障是跟随设备还是端口。设备搬线只能在相关写入已结束后进行，避免制造未标记中断。

## 可复用命令模板

从消费工作区根目录执行，下列路径、Device ID 和 operation ID 均替换为已核对值；它们是人工步骤模板，不是可直接批量执行的脚本。

```sh
python3 mosaico.py doctor --json
python3 mosaico.py iris status --all --json
python3 mosaico.py iris run --project /absolute/path/control_project
```

保留 `iris run` 进程，在另一个终端进行身份收集与显式认领。`iris list` 是被动列表，不能代替初次认领；未知设备通过已发现且核对过的 endpoint 进行初次握手，再固化 Device ID。已有其他项目所有权的设备走 takeover，不能强制清理现场。

```sh
python3 mosaico.py iris list --project /absolute/path/control_project --details --json
python3 mosaico.py iris claim --project /absolute/path/control_project --endpoint VERIFIED_ENDPOINT --json
python3 mosaico.py iris device-status --project /absolute/path/control_project --device-id DEVICE_ID --inventory --json
python3 mosaico.py iris test enter-recovery --project /absolute/path/control_project --device-id DEVICE_ID --timeout 30 --json
python3 mosaico.py iris system-update --device-id DEVICE_ID --bundle /absolute/path/C.irisfw --timeout 900 --json
```

`system-update --bundle` 不能与 `--project` 或 `--skip-build` 合用，上例从工作区根目录运行并使用已核对的默认控制项目。若使用 `system-update --project ... --skip-build`，则改为读取该项目默认构建包，不能再传 `--bundle`。同布局代码更新在目标应用项目已取得该设备所有权后执行；更换 `--project` 不会自动完成设备交接。

```sh
python3 mosaico.py iris app-update --project /absolute/path/A2 --device-id DEVICE_ID --skip-build --validation elf-sha256 --timeout 600 --json
python3 mosaico.py iris device-status --project /absolute/path/A2 --device-id DEVICE_ID --inventory --json
python3 mosaico.py iris logs --project /absolute/path/A2 --device-id DEVICE_ID --snapshot --json
python3 mosaico.py iris memory --project /absolute/path/A2 --device-id DEVICE_ID --json
python3 mosaico.py iris operation-status OPERATION_ID --project /absolute/path/A2 --json
```

前三类超时采用当前默认值：进入 Vibe Mode 30 秒、app-update 600 秒、system-update 900 秒。首轮不调大。期限到达即计一次调用异常，但原写入未必停止；之后只查询原操作。需要继续验证时可通过当前 CLI 的 `iris operation-reconcile OPERATION_ID` 路径处理并记录，不能据查询命令返回 0 推断原操作成功，必须检查原操作结果。

本地构建、包校验和上传不一定已经生成 operation ID。失败时保留该字段为空、完整 stdout/stderr、返回码及提交阶段，不能捏造 ID，也不能把提交前失败归为设备烧录失败。

## 证据与故障现场保护

运行数据保存在消费工作区独立的新目录，如 `.codex-runs/flash-repro/<run-id>/`，每轮独立编号，不覆盖失败文件。运行器后续实现须只调用消费工作区 launcher，提供只读准备模式、全局并发限制、每设备互斥、固定随机种子、失败冻结和安全退出。

每次安装写一条结构化记录，至少包含：

- run/case/设备编号、随机种子、轮次、并发数、同步或异步调度、物理拓扑版本。
- 完整命令及原始输出、进程返回码、UTC 时间、单调时钟耗时、开始/最后进度时间。
- Device ID、USB serial、Base MAC、前后 Boot ID 原始文本、endpoint、Gateway/session/owner、operation/takeover ID。
- 源/目标包摘要、ELF SHA、大小、分区表摘要及每个资源镜像摘要；实际查询结果与期望值分别保存。
- 构建/准备、排队、进入 Vibe Mode、传输/写入、重启、重新枚举、健康验证各阶段耗时；不可观测阶段填空并保存原始事件，不推算为 0。
- 首次结果、最终结果、重试次数、是否人工介入、介入前状态及采取的具体动作。

全局保留 Gateway/CLI 日志和 USB 枚举事件；每次安装前后保存 live inventory，目标稳定启动后间隔 5 秒再复查一次身份、ELF 和 healthy。每十次安装采样一次内存，阶段开始和结束读取 crash 基线。日志较重的持续跟踪单独作为观测负载变体，避免把采集开销混入基线。

首次异常按以下顺序处理：

1. 冻结该设备后续写入，保存原命令、operation ID、最近日志和 USB/所有权状态；先确认是否仍有写入在进行。
2. 每 5 秒查询一次原 operation，记录晚完成、failed 或 unknown。调用超时后额外观察最多 180 秒用于分类，不能因此宣称原期限内成功，也不能据观察期结束认定写入器已经退出。
3. 可达时保存 live inventory、内存与崩溃证据；崩溃归档带操作影响的情况在原快照之后单独记录。不可达时保留查询失败和 OS 枚举，不能把断连设备替换成另一台。
4. 确认仅影响单设备且不存在误写/共享锁异常时，让其他设备继续；出现错设备写入、保护区变化、跨设备复位或共享锁异常时暂停该 Gateway 全部新写入，保留已有写入器，不强杀写入进程。
5. 收集现场后，再逐级尝试恢复：继续验证原操作、正常重新连接、明确所有权交接、重启会话、物理复位/拔插、授权后的 ROM 恢复。每一步单独记录结果，不自动跳到 `recover`。

对无人为注入的异常，任何需要 CLI 重启、重新认领或物理动作才能继续的结果，都计入“需要介入”；脚本自动完成这些补救也不能算首次成功。注入用例的预期恢复与自然故障分别统计。

## 结果判定与缩小复现

主指标是首次安装成功率、每设备/每阶段失败率、需介入次数与每千次安装介入率。另报最终成功率、晚完成次数、每阶段 p50/p95/最大耗时、实际吞吐、复位/重枚举次数及主机/设备内存趋势；批量完成数不能替代每设备分母。

基础测试通过要求：身份和内容验证正确、非目标设备无意外重启、保留数据无意外变化、零自然故障和零介入。注入测试要求恢复结果符合产品契约且其他设备可用，不能用零超时作为判定标准。即使当前计划的 724 次安装均成功，也只报告“在该版本、包、接线和负载下未复现”，不能推断没有低概率问题。

发生问题后，固定失败包、种子和前一轮状态，只比较故障设备单台与九台并发；再分别减少镜像大小、资源组件数、布局变化和项目交接。每次只移除一个变量，先重放 1 至 3 次并记录命中次数，形成可重复用例后再安排修复回归。用实际失败/总次数描述差异，不能以一次未触发证明问题消失。

交付一份最小复现记录：具体设备及接线、应用和工具 revision、冻结包摘要、准备状态、逐条命令、失败阶段、原操作结果、人工恢复动作，以及相同条件下的失败/总次数。附九设备统计和现场证据目录；功能修复后用该最小用例及曾触发问题的完整阶段回归。
